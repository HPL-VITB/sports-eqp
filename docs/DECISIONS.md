# Architecture decisions

Changes from, or details added to, the Phase 1 blueprint. Newest first.

## 2026-11-17 · Phase 8

1. **Release is 1.0.0-rc.1, not 1.0.0.** It becomes 1.0.0 after the first successful Next.js build in CI and the user
   acceptance test on the live site. Neither can be run from the development environment (no package installs or network).
2. **Page checks with stand-ins.** Pages are type-checked and rendered against minimal React/Next.js stand-ins
   (`tools/preview/`). This catches wrong props, wrong data access, crashes, role leaks and layout problems early. It does not
   replace `next build` or a real browser session, which CI and the UAT cover.
3. **Content-Security-Policy allows inline scripts and styles** (needed by Next.js without per-request nonces) but no
   third-party origins, no framing and no plugins. Nonce-based CSP can be added later if required by university IT.
4. **Production refuses to start** with a missing or short `CRON_SECRET` or with `.env.example` secrets; the job secret is
   compared in constant time.
5. **Backups go to private GitHub Actions artifacts, encrypted (AES-256, passphrase held offline), kept 30 days,** and are
   off by default. They contain personal data, so the university may prefer its own storage; the workflow is easy to redirect.
6. **Hosting advice: Vercel Pro (or the university's existing hosting).** Vercel's Hobby plan is limited to personal,
   non-commercial use; a department's operational system does not fit that. The app itself runs on either plan.
7. **Phone layout fixes found by the page checks:** sign-out reachable on phones, no blank band under the menu on short pages,
   stacked tables left-aligned with empty fields hidden, reference numbers kept on one line. A report opened by a role that
   may not see it now shows the access page instead of an error.

## 2026-11-17 · Phase 7

1. **PDF generated by a small built-in writer** (`src/server/reports/pdf.ts`, standard Helvetica, no embedded fonts) rather than
   a headless browser or a PDF library. It keeps the serverless function small and needs no package install. Limitation: only
   Latin characters (Windows-1252) print; other scripts show as "?". Names at VIT Bhopal are entered in English, so this is
   acceptable; revisit if Hindi names are needed in PDFs (Excel is unaffected).
2. **Long text in PDFs is shortened with "…"** to keep one line per record; the Excel file always has the full text.
3. **On-screen reports show the first 500 rows**; downloads include up to 20,000 (PDF up to 5,000, beyond which Excel is advised).
4. **Default date range is the last 90 days** for date-based reports; the stock register is always "as of now".
5. **Report access is a fixed list per role** (see README), checked on the server for the page, the data and the download.
6. **Overdue is computed at report time** in IST from the due date, so a report printed tomorrow shows tomorrow's figures.

## 2026-11-17 · Phase 6

1. **Who requests and who approves.** Following the permissions matrix, the ASO and storekeepers request discards and corrections;
   only FR Sports approves; nobody approves their own. Stock counts can be done by FR Sports, the ASO or a storekeeper, but the
   corrections a count produces cannot be approved by the person who submitted it. In practice: the ASO or a storekeeper counts,
   FR Sports approves. If FR Sports does the count, a second FR Sports user must approve.
2. **Automatic discards for used-up consumables** have no human requester, so the FR Sports user who recorded the return may approve them.
3. **Held units:** a pending discard of store units holds them out of "available to issue"; a pending discard of damaged or missing
   units holds them on their damage / missing record.
4. **Corrections apply to usable and damaged stock only** (what is on the shelf). Issued and missing stock is changed only through
   returns, recovery and discards, so every unit stays traceable to an issue or record. Damaged corrections open or close damage
   records so those always match the Damaged count.
5. **Only one pending correction per item and stock type**, and only one open count per sport / category / location / whole store.
6. **Reversal is limited to receipts and opening stock.** Issues, returns and other changes are corrected through their own flows,
   which keeps issue and damage records consistent.

## 2026-11-17 · Phase 5

1. **Photos are stored in PostgreSQL** (compressed to ~300 KB in the browser, 1.5 MB maximum) instead of Vercel Blob. One fewer
   service and account; the photos share the database's backups and access rules. Neon's free 1 GB holds about 2,000-3,000
   photos alongside the records; they can be moved to object storage later without changing the screens.
2. **Used-up consumables** are moved to Missing and recorded as a CONSUMED incident with a mandatory note. Phase 6 turns each one
   into a discard request for FR Sports, as the blueprint describes; until then they stay open under Damage, missing & discards.
3. **Missing units recorded as found but damaged** move to Damaged and get their own damage incident, so every damaged unit can be
   traced to a record.
4. **One daily job** (`/api/cron/daily`) replaces the separate housekeeping job, because Vercel's free plan limits cron jobs.
5. **Missed reminder days are caught up with the reminder due now only** (no burst of old reminders).
6. **The "Adjustments & Discards" menu is renamed "Damage, missing & discards"** while only damage and missing records exist.

## 2026-11-16 · Phase 4

1. **Request limits:** at most 20 different items per request, 5 pending requests per person, and a return date no more than
   30 days ahead (`MAX_LOAN_DAYS`). Requests above current availability are refused at once, with the available number shown.
2. **The approver may issue fewer than requested or leave a line out** (quantity 0). The emails show what was actually issued.
3. **Recipients may cancel their own pending requests** (status Cancelled).
4. **"Ready for handover"** is a flag that store staff set after picking the equipment; it moves no stock and approval still
   happens at handover, as the binding decisions require.
5. **Email sending ceiling of 1,500 per rolling 24 hours** from the outbox, below Google Workspace's per-account limit, leaving
   room for sign-in codes. Emails above the ceiling wait, they are not dropped.
6. **"Delivered" is not tracked:** SMTP only confirms that the university mail server accepted the message, so the last
   verifiable state is "Accepted by mail server".
7. **Rejection emails** are sent to the requester (not required by the brief, but it saves them checking the portal).

## 2026-11-16 · Phase 3

1. **Excel files are read and written with a small module on JSZip** (`src/server/inventory/spreadsheet.ts`) instead of ExcelJS.
   It handles what the import needs (first worksheet, text and numbers) and is tested against files saved by LibreOffice and
   openpyxl. ExcelJS can still be added in Phase 7 if formatted report exports need it. `.csv` is accepted too; old `.xls` is not.
2. **Stock changes in one TypeScript module, not database functions.** `ledger.ts` is the only code that writes `item_stock`;
   the database backs it up with CHECK constraints, an append-only trigger on history and a ledger consistency view.
3. **Import permissions follow the role matrix row by row:** Procurement can add stock to existing items only; FR Sports and
   the ASO can also create new equipment; only FR Sports can create new categories during an import. Storekeepers cannot import.
4. **Rows for the same equipment in one file are combined** into one stock addition, shown as "Combined" in the preview.
5. **Seeded data:** one location ("Central Sports Store") and 11 sports with 2-4 letter codes (CRI, FTB, BSK, VOL, BAD, TT, TEN,
   PKB, CHS, ATH, GEN). Categories are added by FR Sports or through an FR Sports import.
6. **Stock receipts are recorded in the movement ledger, not duplicated in the audit log.** The ledger already holds who, when,
   quantity and before/after; master-data and item edits go to the audit log.

## 2026-11-16 · Phase 2

1. **Plain SQL through a small `Db` interface instead of Drizzle ORM.** Every stock operation in later phases needs explicit
   `SELECT … FOR UPDATE`, conditional `UPDATE … WHERE status = …` and advisory locks. Writing them as SQL keeps the locking visible
   in review and removes a dependency. `src/server/db/types.ts` is the whole contract; `src/server/db/pg.ts` implements it with
   node-postgres.
2. **Plain CSS (`src/app/globals.css`) instead of Tailwind + shadcn/ui.** The interface is tables and forms; one small stylesheet is
   easier for a future maintainer than a CSS framework. Can be revisited before Phase 3 if preferred.
3. **Business logic lives outside Next.js** (`src/server/**`, standard `Request → Response` handlers). Next.js route files only
   forward. This lets the security-critical code be tested end-to-end without a running web server.
4. **Rate limits and sessions are stored in PostgreSQL**, not Redis. Traffic is small; one fewer service to run.
5. **Profile category** covers individuals only (student, faculty, staff, coach, sports coordinator). Teams, houses, hostel blocks,
   departments and events will be a field on each request, with the signed-in requester as the accountable individual.
6. **Sign-in domain** is exactly `vitbhopal.ac.in` (sub-domains are not accepted). Configurable via `ALLOWED_EMAIL_DOMAINS`.
7. **Append-only tables** are enforced by a database trigger (`forbid_update_delete`), which also works when the app's database user
   owns the tables (as on Neon).
